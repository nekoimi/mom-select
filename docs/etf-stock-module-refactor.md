# ETF 与个股双模块改造设计

> 状态：第一版已实施，后续按本文继续演进  
> 更新日期：2026-08-13

## 1. 背景

`mom-select` 当前只面向 ETF 动量轮动，行情获取、标的池构建、策略计算、报告生成和 CLI 编排均位于 `mom_select/` 单层包中。后续计划增加个股趋势选股，但系统定位保持不变：**只生成排名、推荐和复核报告，不连接证券账户，不执行交易下单**。

ETF 和个股虽然可以复用交易日历、行情缓存、通知等基础能力，但在标的池、数据质量、风险过滤、指标模型和报告语义上有明显差异。若直接在现有函数中增加大量 `asset_type` 条件分支，两个策略会相互影响，后续测试和维护成本也会持续增加。

本次改造的核心目标是将 ETF 和个股拆成两个独立业务模块，同时仅共享稳定、无业务偏向的基础设施。

截至 2026-08-13，项目已建立 `core/`、`etf/`、`stock/` 模块边界，完成全市场个股预筛、多周期趋势排名、独立报告、CLI 子命令和双任务调度。为保持现有用户兼容，ETF 的旧实现文件暂时保留为兼容层，后续阶段再逐步将实际实现完全迁入 `etf/`。

## 2. 目标与非目标

### 2.1 目标

- ETF 与个股拥有独立的配置、模型、标的池、策略、报告和运行入口。
- 保持现有 ETF 策略行为、配置和 `mom-select` 默认命令兼容。
- 共享交易日历、通用行情协议、缓存、通知和基础数学计算。
- 个股首版从全市场 A 股清单动态构建候选池，在收盘后生成趋势排名报告。
- 两类任务可以独立启停、独立调度、独立失败，不因其中一个模块异常阻塞另一个模块。
- 缓存、报告和状态文件按资产类型隔离，便于排障和归档。
- 为后续扩展个股行业比较、基本面过滤或新的数据源保留清晰接口。

### 2.2 非目标

- 不接入券商账户，不实现自动下单、撤单、仓位同步或成交回报。
- 个股首版不生成盘中 13:05 信号，默认只使用完整收盘数据。
- 不强行统一 ETF 与个股的完整指标对象、策略参数或报告模板。
- 不在本次改造中改变现有 ETF 策略公式和筛选阈值。

## 3. 当前结构与主要问题

当前核心结构：

```text
mom_select/
  cli.py             ETF 运行编排
  config.py          ETF 默认路径和市场指数
  data.py            行情、多数据源回退和缓存
  models.py          ETF 策略与报告模型
  strategy.py        市场判断、动量指标和目标选择
  universe.py        ETF 固定池和动态池
  portfolio.py       人工持仓读取
  reporting.py       ETF 多格式报告
  calendar.py        交易日历
  notifications.py   消息通知
  settings.py        YAML 配置加载
scripts/
  mom_select_scheduler.py
```

主要问题：

- `cli.py` 同时承担时间校验、数据获取、候选池构建、指标计算、报告生成和状态保存，职责过重。
- `data.py` 的公开接口和实现主要围绕 ETF 命名，直接扩展个股容易混入复权、停牌、ST 和涨跌停等特有逻辑。
- `StrategyConfig`、`EtfMetrics`、`AdviceReport` 放在同一通用模型文件中，新增个股后容易形成含大量可选字段的通用模型。
- 当前只有一套 `schedule`、`paths` 和 `strategy` 配置，无法独立控制两类任务。
- 缓存、报告和市场状态没有资产类型命名空间。
- 调度器直接依赖 ETF CLI 的参数结构，不适合作为双业务模块的长期入口。

## 4. 设计原则

1. **业务隔离**：ETF 和个股各自拥有完整业务链路，不通过散落的条件分支共用策略流程。
2. **依赖单向**：`etf` 和 `stock` 可以依赖 `core`，`core` 不依赖任一业务模块。
3. **模型独立**：共享基础类型，业务指标和报告模型分别定义。
4. **兼容优先**：先移动和封装现有 ETF 行为，再增加个股能力。
5. **失败隔离**：单个任务或通知渠道失败必须记录完整日志，不影响其他已配置任务。
6. **数据可追溯**：报告记录数据截止日期、运行模式、数据源警告和不可执行原因。

`service.py` 是每个业务模块的应用入口，负责串联数据、策略和报告；策略模块只处理传入的数据，不直接访问网络或写文件。

## 6. 模块职责与复用边界

| 能力 | 归属 | 说明 |
|---|---|---|
| 中国交易日历 | `core` | 两类任务使用同一交易日判断和缓存 |
| 通知渠道 | `core` | 发送机制共享，标题和正文由业务模块生成 |
| HTML 转 PNG、原子写文件 | `core` | 只提供渲染基础能力，不包含业务字段 |
| 回归斜率、R²、ATR 等纯函数 | `core` | 无 ETF/个股语义时才下沉 |
| 行情数据协议 | `core` | 统一输入输出结构，不统一不同证券的数据规则 |
| 数据源适配 | 业务模块 | ETF 和个股分别处理代码、复权和字段差异 |
| 市场状态 | `core` 或独立策略组件 | 输入指数数据，输出通用市场环境，不决定具体标的 |
| 标的池 | 各业务模块 | ETF 池与个股全市场动态候选池完全分开 |
| 策略参数和指标 | 各业务模块 | 禁止用一个大配置或大量可选字段覆盖两类资产 |
| 报告内容 | 各业务模块 | 允许共享页面外壳，不共享业务表格模型 |

共享代码的判断标准：至少被两个模块真实使用，并且不需要通过 `asset_type` 分支改变行为。否则先保留在业务模块内。

## 7. 外部入口设计

### 7.1 CLI

兼容现有行为：

```bash
# 继续执行 ETF 盘中策略
uv run mom-select

# 显式执行 ETF
uv run mom-select etf

# 执行个股收盘趋势排名
uv run mom-select stock --mode close
```

迁移期由顶层 `mom_select.cli` 负责分发。无子命令时按现有 ETF 参数解析，避免破坏 Docker、Supervisor 和用户脚本。稳定后可以提示用户逐步迁移到显式子命令，但不急于删除兼容入口。

### 7.2 Python 服务接口

建议每个模块暴露独立的请求和结果类型：

```python
etf_result = etf.service.run(EtfRunRequest(...))
stock_result = stock.service.run(StockRunRequest(...))
```

不再让调度器构造 ETF CLI 使用的 `argparse.Namespace`。CLI 和调度器都调用相同的服务接口，参数校验由请求模型负责。

## 9. 个股首版方案

### 9.1 全市场候选池

个股模块不维护固定股票池。每次正式任务从数据源获取当前全市场 A 股清单，再执行资格过滤并构建当日候选池。全市场清单应缓存到 `data/cache/stock/universe.csv`，记录数据源和更新时间；在线获取失败时，可以使用仍在有效期内的缓存，并在报告中明确提示。在线数据和有效缓存均不可用时，任务停止，不能使用不完整列表生成正式排名。

候选池构建顺序：

1. 获取全市场 A 股证券清单及板块、简称、上市日期、交易状态等元数据。
2. 获取用于资格过滤的最新有效未复权收盘价或收盘快照。
3. 应用必要硬性筛选条件。
4. 对剩余股票进行数据完整性、上市时间和流动性过滤。
5. 只为通过预筛的股票拉取或读取完整历史行情并计算趋势排名。

采用“先用全市场快照预筛，再加载历史行情”的两阶段流程，避免对所有股票逐只请求长周期数据。若数据源支持批量行情或全市场日线，应优先使用批量接口。

### 9.2 数据要求

个股模块至少需要：

- 全市场 A 股清单及所属板块；
- 前复权日线 OHLCV 和成交额；
- 用于股价门槛判断的最新有效未复权价格；
- 证券简称、上市日期和交易状态；
- ST、`*ST`、退市整理标识；
- 停牌状态；
- 涨跌停状态或可用于推导涨跌停的字段；
- 所属行业；
- 用于相对强弱比较的基准指数行情。

趋势计算使用一致的前复权价格序列，数据源必须在结果中标明复权方式，不能将不复权与前复权行情混合进入同一次趋势计算。`股价 < 100 元` 是现实价格门槛，必须使用最新有效的未复权收盘价判断，不能使用历史前复权价格判断。

### 9.3 资格过滤

以下条件是进入个股趋势排名的必要条件，任一项不满足即排除：

- 非创业板；
- 非科创板；
- 非 ST，包含 `ST`、`*ST` 及其他数据源标记为风险警示的股票；
- 最新有效未复权股价严格小于 100 元。

板块判断应优先使用数据源提供的市场和板块字段；代码规则仅作为校验或降级手段。当前 A 股代码规则中，创业板通常为 `300`、`301` 开头，科创板通常为 `688`、`689` 开头，但实现时应测试数据源的完整代码范围，避免只靠硬编码前缀遗漏新规则。

当前必要条件没有排除北交所，因此实现不得自行将北交所作为硬排除项；数据源清单中的北交所股票仍按 ST、价格、上市时间、流动性和交易状态等规则处理。后续如需仅保留沪深主板，应作为一项新的显式配置和筛选规则加入。

通过上述必要条件后，继续执行数据质量和风险过滤：

- 退市或退市整理标的；
- 当日停牌或关键行情字段缺失的标的；
- 上市交易日不足配置门槛的标的；
- 平均成交额低于流动性门槛的标的；
- 连续涨跌停等不适合人工跟踪的异常状态。

被排除的股票及原因应进入统计。报告至少展示每类规则的排除数量，并对进入历史数据阶段后被排除的股票保留明细，避免在 HTML 中直接铺开数千条全市场预筛记录。JSON 报告可以保留完整排除明细或输出独立明细文件。

### 9.4 趋势评分

个股首版建议采用可解释的多维排名，而不是直接复用 ETF 的单窗口得分：

| 维度 | 建议指标 | 目的 |
|---|---|---|
| 中短期趋势 | 20 日收益、MA20 斜率 | 捕捉近期方向 |
| 中期趋势 | 60 日收益、MA20/MA60 排列 | 避免只看短期脉冲 |
| 长期趋势 | 120 日收益、价格相对 MA120 | 判断大级别趋势 |
| 相对强弱 | 相对沪深 300 的 20/60 日超额收益 | 排除仅随市场普涨的标的 |
| 趋势质量 | 线性回归 R² | 偏好平滑趋势 |
| 风险 | ATR、最大回撤、下行波动 | 对高波动和深回撤降权 |
| 流动性 | 近 20 日平均成交额 | 保证结果可人工执行和复核 |

总分由各维度标准化后加权得到，并同时展示原始指标。首版阈值和权重应通过配置表达，默认值需要在实现阶段使用历史样本验证，不能只凭经验固定。

### 9.5 输出语义

个股报告建议分为：

- 市场环境和数据截止时间；
- 全市场清单数量、各硬性条件排除数量、最终分析池大小和数据覆盖率；
- 趋势排名 Top N；
- 每只股票的趋势、相对强弱、风险和流动性指标；
- 风险提示与人工复核清单；
- 推荐关注结论，而不是买卖指令。

报告用语使用“关注”“候选”“排名”“不满足条件”，避免“买入”“卖出”或具体委托数量等交易执行语义。

## 10. 调度设计

调度器读取所有 `enabled=true` 的任务并分别注册：

```text
交易日历
  ├─ 13:05 ETF 盘中任务
  └─ 15:20 个股收盘任务
```

每个任务执行前都检查交易日历。个股任务还需确认目标日期的收盘行情已完整；若数据尚未就绪，应记录原因并跳过报告或标记报告不可执行，不使用盘中未完成日 K 代替收盘数据。

建议任务 ID 固定为：

- `daily-etf-advice`
- `daily-stock-ranking`

两个任务分别设置 `max_instances=1`、`coalesce=true` 和误触发宽限。执行异常在任务边界完整记录堆栈，通知失败只影响对应渠道，不应使另一业务任务停止。

`--run-once` 后续需要增加任务选择：

```bash
uv run python scripts/mom_select_scheduler.py --run-once --task etf
uv run python scripts/mom_select_scheduler.py --run-once --task stock
```

## 11. 数据源与缓存

### 11.1 数据源接口

`core` 只定义通用协议，例如历史 K 线、证券信息和交易状态；ETF 与个股各自组合数据源和回退顺序。不能假定所有来源都提供相同复权、成交额和状态字段。

个股数据源接入前需要验证：

- 全市场 A 股清单是否完整，板块字段能否可靠区分创业板和科创板；
- A 股代码映射是否完整；
- 最新未复权价格、证券简称及风险警示状态是否处于同一有效日期；
- 前复权参数和复权因子是否稳定；
- 停复牌、ST、上市日期和涨跌停字段是否可获取；
- 历史数据修订和缓存更新规则；
- 限流、超时、批量请求能力和许可范围。

AKShare 可以作为个股数据适配器之一，但应继续保留可替换的数据协议和回退机制，不能让策略直接依赖 AKShare 返回字段。

### 11.2 存储隔离

```text
data/
  cache/
    shared/
      trading_calendar.csv
      indexes/
    etf/
    stock/
  state/
    etf/
      market_state.json
    stock/
reports/
  etf/
  stock/
```

交易日历和明确采用相同口径的指数行情可以共享。证券行情缓存必须隔离，以防同代码表示、字段格式或复权规则冲突。缓存元数据至少记录数据源、更新时间、复权方式和字段版本。

## 12. 报告与通知

ETF 与个股分别生成 Markdown、JSON、HTML 和 PNG。可共享页面基础样式和文件输出流程，但业务表格由各自模块维护。

建议报告文件名带业务前缀：

```text
reports/etf/etf_advice_20260813_1305.html
reports/stock/stock_ranking_20260813_close.html
```

通知标题明确区分业务和运行模式：

```text
ETF 动量策略日报 2026-08-13
个股趋势排名日报 2026-08-13
```

通知层接收已经准备好的标题、摘要和附件，不读取策略对象，也不判断 ETF 或个股。发送请求、API 响应错误和异常堆栈继续写入标准输出/错误，确保 Docker 中可通过 `docker compose logs` 查看。

## 13. 分阶段迁移计划

### 阶段一：建立回归基线

- 固定当前 ETF 典型输入对应的排名、目标、报告字段和文件名。
- 补充 CLI、配置兼容、调度和失败日志测试。
- 保留当前 README 和 Docker 使用方式不变。

完成标准：当前测试全部通过，并有 ETF 结果快照或等价契约测试保护行为。

### 阶段二：抽取共享基础设施

- 移动交易日历、通知和通用报告写入能力到 `core`。
- 抽取纯数学函数和通用数据类型。
- 在旧模块保留导入兼容层，避免一次性修改所有调用者。

完成标准：没有策略行为变化，现有 CLI、调度器和报告输出仍可用。

### 阶段三：迁移 ETF 模块

- 将 ETF 模型、数据、标的池、策略、持仓和报告迁入 `mom_select/etf/`。
- 将超长 CLI 编排拆到 `etf/service.py`。
- 顶层 CLI 保持无子命令时执行 ETF 的兼容行为。
- 将 ETF 缓存、报告和状态切换到独立命名空间，并提供旧目录读取兼容。

完成标准：同一输入下关键 ETF 排名和建议与改造前一致。

### 阶段四：实现个股最小版本

- 增加个股配置模型及全市场证券清单缓存。
- 接入全市场 A 股清单、未复权最新价格、前复权日线、证券状态与行业数据。
- 实现非创业板、非科创板、非 ST 和股价小于 100 元的必要预筛。
- 实现资格过滤、多周期趋势评分和独立报告。
- 只提供手动命令执行，先不启用生产定时任务。

完成标准：全市场清单可稳定收敛为可解释的候选池并生成收盘排名，所有排除规则都有数量统计和可追溯原因。

### 阶段五：接入独立调度与通知

- 调度器注册 ETF 和个股两个任务。
- 增加任务级启停和 `--task` 单次执行。
- 验证交易日跳过、收盘数据完整性、异常隔离和通知日志。
- 更新 Docker、配置示例、README 和部署文档。

完成标准：容器中两个任务可独立运行、独立失败和独立查看报告与日志。

## 14. 测试策略

### 14.1 共享核心

- 交易日历缓存、刷新失败和覆盖日期不足；
- 缓存元数据及复权口径校验；
- 数学函数使用固定数组验证边界和数值稳定性；
- 通知渠道成功、API 错误、超时及敏感信息脱敏。

### 14.2 ETF 回归

- 当前市场状态切换逻辑；
- 动态池与固定池合并；
- 13:05 快照覆盖率和成交量折算；
- 持仓保留、空结果转防御 ETF；
- 现有报告核心字段和 CLI 参数兼容。

### 14.3 个股模块

- 全市场清单获取、缓存回退、缓存过期和清单不完整；
- 创业板 `300/301`、科创板 `688/689` 及板块元数据识别；
- `ST`、`*ST`、大小写和数据源风险警示标记识别；
- 未复权价格 `< 100`、等于 100、缺失和日期过期的边界；
- 前复权行情映射和缓存隔离；
- ST、停牌、上市时间、流动性和异常状态过滤；
- 20/60/120 日窗口数据不足；
- 相对强弱、均线排列、R²、ATR 和回撤计算；
- 排名稳定性、同分规则和 Top N 截断；
- 数据覆盖不足时报告不可执行；
- 报告不出现交易下单语义。

### 14.4 集成测试

- 同一交易日依次执行两个任务；
- ETF 失败时个股仍可执行，反之亦然；
- 非交易日两个正式任务均跳过；
- 两类缓存、报告和状态不会相互覆盖；
- Docker 标准日志包含任务名称、日期、阶段和完整异常堆栈。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 一次性移动文件过多 | 难以定位 ETF 回归 | 分阶段迁移，保留兼容导入和契约测试 |
| 个股复权口径不一致 | 趋势指标失真 | 缓存记录复权方式，同次运行强制统一 |
| 全市场请求量较大 | 任务超时、数据源限流 | 批量快照先预筛、并发限速、增量缓存，再获取候选历史行情 |
| 免费接口限流或字段变化 | 数据缺失、筛选错误 | 适配层校验字段、缓存全市场清单并支持数据源回退 |
| 股票状态数据滞后 | 报告包含不可交易标的 | 显示状态时间和人工复核项，覆盖不足时不可执行 |
| 通用层过度抽象 | 两类业务再次耦合 | 只抽取稳定且实际复用的能力 |
| 双任务同时请求数据 | 请求峰值和缓存竞争 | 错峰调度、缓存原子写入、按资产隔离目录 |
| 配置升级破坏部署 | 现有容器无法启动 | 自动映射旧 ETF 配置并记录弃用提示 |

## 16. 验收标准

改造完成需同时满足：

- `uv run mom-select` 的默认 ETF 行为保持兼容。
- `uv run mom-select etf` 和 `uv run mom-select stock` 均可独立运行。
- ETF 与个股不存在共享完整策略模型或报告模型。
- 两类业务的缓存、报告和状态文件路径明确隔离。
- 个股从全市场 A 股清单动态构建候选池，不依赖人工固定池。
- 创业板、科创板、ST 和最新有效未复权股价大于等于 100 元的股票不会进入排名。
- 趋势指标使用完整前复权收盘数据，价格门槛使用同一交易日的未复权价格。
- 各必要筛选条件以及停牌、上市时间不足和流动性不足等排除原因可在报告中追溯。
- 两类定时任务都只在交易日运行，并能独立启停和失败隔离。
- 所有异常包含任务名称和完整堆栈，Docker 日志可直接查看。
- README、配置示例、Docker/Compose 和部署文档与新入口一致。
- Ruff 和完整 pytest 测试通过。

## 17. 实施前待确认事项

以下事项不阻塞目录改造，但应在实现个股模块前确定：

1. 个股首选数据源及备用源，以及各自的复权与许可边界。
2. 全市场清单和快照缓存的有效期，以及清单完整性阈值。
3. 趋势各维度的初始权重、Top N 数量和最低合格分数。
4. 个股报告是否只做观察名单，还是结合人工持仓给出“继续关注/移出关注”结论。
5. 股票状态和收盘行情最晚可接受的到达时间，是否需要延迟重试。

在这些决策完成前，可以先实施阶段一至阶段三，完成结构拆分且不改变现有 ETF 功能。
